# LinkChat Protocol — `linkchat/1`

Status: experimental. This document specifies the wire protocol as
implemented in this repository. Where the implementation falls short of what
a production system would need, this document says so rather than implying
otherwise.

---

## 1. Scope

LinkChat turns a shareable link into a conversation. The link identifies the
conversation and carries the key material needed to participate. Participants
are identified by cryptographic keys they generate themselves. Messages are
signed, end-to-end encrypted, and replicated between participants over
whatever transport is available — a direct connection when one exists, SMTP
store-and-forward when one does not.

The protocol version string is `linkchat/1`. It appears in every record and
every frame. A peer MUST reject anything carrying a version it does not
implement.

### Layering

```
IDENTITY      an Ed25519 key pair, generated on the device
   |
CONVERSATION  a set of participants and a shared symmetric key
   |
RECORD        a signed, encrypted, replicated log entry
   |
FRAME         a signed envelope carrying records or control traffic
   |
TRANSPORT     P2P (WebSocket), SMTP, or in-process
```

Each layer depends only on the one above it. Transports move opaque frames
and are interchangeable; nothing above the transport layer knows which one
carried a message.

## 2. Identity

An installation generates an **Ed25519 key pair** on first run.

```
peer_id = "p_" || crockford_base32(sha256(public_key)[0..10])
```

The peer id is a fingerprint of the public key, so a claimed identity can
always be checked against the key that signs for it. Any peer id that does
not match the accompanying public key MUST be rejected (`bad_peer_id`).

The private key never leaves the device. It is stored in `identity.json` with
mode `0600`, and when `LINKCHAT_KEY_PASSPHRASE` is set it is wrapped with
scrypt (N=2^15, r=8, p=1) and AES-256-GCM, with the peer id bound in as
associated data. With no passphrase the key is stored in the clear, exactly
like an unencrypted SSH key; `linkchat identity` says so plainly.

**An email address is not an identity.** It is an optional delivery hint
attached to an identity, published in join and profile records. Two
installations sharing an address are two peers. A peer that changes address
is the same peer.

## 3. Conversations

A conversation has:

| Field | Meaning |
| --- | --- |
| `conversation_id` | `c_` + ULID (48-bit timestamp, 80 bits random, Crockford base32) |
| conversation key | 32 random bytes; the AES-256-GCM key all record bodies are encrypted under |
| invite secret | 32 random bytes; the HMAC key that authenticates invitations |
| participants | derived from the log, not stored separately |
| message history | the record log |

The conversation key and the invite secret are generated by the creator. The
conversation key is distributed **in the link**. The invite secret is
distributed **in the genesis record**, never in a link — see §4.

### Genesis

The creator's first record is a `join` carrying `invite_secret`. This is the
genesis record. Every node independently identifies it as *the first `join`
in total order that carries an invite secret*, and its sender as the creator.
Because the ordering is total and deterministic, every node agrees.

## 4. The link

```
https://linkchat.local/join/c_01JX8Q…#v=1&k=…&n=…&e=…&m=…&h=…&c=…
└──────────── path: public ─────────┘ └─────── fragment: secret ──────┘
```

The custom-scheme form `linkchat://join/<conversation>#<same fragment>` is
equivalent and parses identically.

| Param | Contents |
| --- | --- |
| `v` | link format version (`1`) |
| `k` | conversation key, 32 bytes, base64url |
| `n` | invite nonce (names this invite for revocation) |
| `e` | invite expiry, epoch milliseconds |
| `m` | invite MAC, base64url |
| `h` | transport hints, base64url JSON array |
| `c` | inviting peer id (advisory, for display) |

Everything secret is in the **fragment**. Browsers do not send fragments to
servers, so an invite pasted into a URL bar does not leak its key to the site
hosting the landing page, and the key never appears in an HTTP log. The path
contains only a random conversation id, which grants nothing on its own.

### The invite token

```
mac = HMAC-SHA256(invite_secret, canonical_json({conversation_id, nonce, exp}))
```

The invite secret is **not** in the link. A link holder can present the token
they were given but cannot mint a new one or extend an expiry — the MAC would
not verify. That is what makes expiry and revocation binding on someone who
only has a link.

Once a peer joins, it receives the invite secret from the genesis record and
can mint invites of its own. This is intended: participants can invite.

### Validation

A peer admitting a join MUST check, in order:

1. the MAC verifies under the conversation's invite secret (`invite_invalid`);
2. the nonce has not been revoked (`invite_revoked`);
3. the invite has not expired (`invite_expired`).

There are two evaluation contexts, deliberately:

- **Live admission** (`Conversation.admits`), performed by whichever
  participant is handling the connection, uses the **local clock**. This is
  the check that stops a replayed or backdated join from resurrecting an
  expired invite against a peer that is online.
- **Log evaluation** (`computeConversationState`) uses the **join record's own
  timestamp**, so that every node — including one that syncs the record a week
  later — reaches the same verdict. Convergence requires determinism, and
  determinism forbids using the local clock.

### Revocation

A `revoke_invite` record names the nonce **and** the participants it
grandfathers: those already admitted under that nonce when the revocation was
written. Anyone else presenting that nonce afterwards is refused, on every
node, permanently.

Naming the grandfathered set explicitly is not incidental. A Lamport clock
cannot distinguish "already joined" from "joining concurrently" — a fresh
joiner's clock always starts at 1 — so a clock comparison would either eject
existing participants or never take effect. Stating the set makes the outcome
deterministic, and denies the concurrent case, which is the safe default for
a revocation.

### What the link grants

**Possession of the link is the ability to read the conversation.** The
conversation key is in it. Anyone who obtains the link — forwarded, screenshot,
found in a chat history — can decrypt any record they can obtain, and can join
until the invite expires or is revoked. This is the premise of the product,
not an oversight, and any deployment must treat the link with the care its
contents deserve. Mitigations that exist: invites expire (24h default) and are
revocable; joining still requires reaching a participant; every message is
attributed to a key, so an interloper cannot impersonate anyone.

## 5. Records

A record is the durable unit. It is signed by its author and encrypted to the
conversation.

```json
{
  "header": {
    "protocol": "linkchat/1",
    "type": "text",
    "conversation_id": "c_01JX8Q…",
    "message_id": "m_01JX8R…",
    "sender_id": "p_3F9K…",
    "sender_key": "<base64url Ed25519 public key>",
    "timestamp": "2026-08-29T12:34:56.789Z",
    "seq": 42,
    "lamport": 117
  },
  "body": { "nonce": "…", "ciphertext": "…", "tag": "…" },
  "signature": "<base64url Ed25519 signature>"
}
```

- **`body`** is AES-256-GCM over the plaintext payload, keyed by the
  conversation key, with `canonical_json(header)` as **associated data**. A
  header cannot be edited without breaking decryption, and a body cannot be
  moved onto a different header.
- **`signature`** is Ed25519 over `canonical_json({header, body})`.
- **`sender_key`** is carried inline so a receiver can verify a record from a
  peer it has never met.

### Canonical JSON

Signatures are over bytes, so both sides must serialise identically: object
keys sorted lexicographically, no insignificant whitespace, `undefined` keys
omitted, and non-finite numbers rejected as unserialisable.

### Record types and payloads

| `type` | Payload |
| --- | --- |
| `text` | `{ text }` |
| `join` | `{ display_name, transports[], invite?, invite_secret? }` |
| `profile` | `{ display_name, transports[] }` |
| `leave` | `{ reason? }` |
| `revoke_invite` | `{ nonce, grandfathered[] }` |

`transports` entries are `{ kind: "p2p", url }` or `{ kind: "smtp", address }`.
Hints arriving from the network are filtered: only `ws://`/`wss://` URLs and
syntactically valid addresses are kept.

### Acceptance rules

A receiver MUST reject a record unless all hold:

| Check | Error code |
| --- | --- |
| `protocol` is `linkchat/1` | `bad_protocol_version` |
| `conversation_id` matches the conversation it arrived for | `wrong_conversation` |
| `seq` and `lamport` are non-negative integers | `bad_encoding` |
| `sender_key` is 32 bytes and hashes to `sender_id` | `bad_peer_id` |
| the signature verifies | `bad_signature` |
| `timestamp` parses and is not more than 15 minutes in the future | `future_dated` |
| the body decrypts under the conversation key | `undecryptable` |

There is deliberately **no lower bound on age**. A record delivered by SMTP
can legitimately arrive days late. Replay is prevented by message-id
deduplication and per-sender sequence numbers, not by a freshness window.

The decryption requirement doubles as an authorisation gate: appending to a
conversation requires the conversation key, which requires the link.

## 6. Ordering and the log

Each node holds the whole set of records. Delivery order is irrelevant; the
same record arriving twice is a no-op.

- **`seq`** is a per-sender monotonic counter. Gaps in it are what sync
  detects.
- **`lamport`** is a Lamport clock: `max(seen) + 1` on write, `max(local,
  received)` on receipt.

Total order is `(lamport, sender_id, message_id)`. Every node holding the same
set displays the same order. This is **not** wall-clock order: a message
written offline appears where it happened causally, not where its timestamp
claims. Timestamps are for display and for skew checks.

If a sender emits two different records with the same `seq`, both are kept and
the conversation reports a **conflict**. Equivocation is evidence, and
discarding it silently would hide a compromised or buggy peer.

## 7. Frames

Frames are transient envelopes between two nodes over one transport hop.

```json
{
  "protocol": "linkchat/1",
  "sender_id": "p_3F9K…",
  "sender_key": "…",
  "sent_at": 1793280000000,
  "nonce": "<base64url 16 bytes>",
  "frame": { "kind": "records", "…": "…" },
  "signature": "<base64url over canonical_json(everything above)>"
}
```

Every frame on every transport is signed by the **sending node**, which is not
necessarily the author of the records inside: when Bob relays Alice's message
to Carol, the frame is Bob's and the record is still Alice's. Both are
verified independently.

Uniform frame signing exists because SMTP has no connection to bind trust to.
It makes a store-and-forward hop exactly as trustworthy as a socket.

| `kind` | Purpose |
| --- | --- |
| `hello` | opens a connection; carries a challenge |
| `auth` | answers a challenge, accepts or declines |
| `records` | pushes records |
| `sync_request` | "here are my watermarks" |
| `sync_response` | records the requester lacks, plus a `complete` flag |
| `ack` | acknowledgement (diagnostics) |
| `presence` | online/offline notice |

### Frame acceptance

- `sender_key` must hash to `sender_id`; signature must verify.
- `sent_at` may not be more than 5 minutes in the future (`future_dated`) nor
  more than 7 days in the past (`stale`).
- `nonce` must not have been seen inside that window (`replayed`). The replay
  cache expires entries at the same horizon, so a frame can never outlive its
  entry.

### Handshake

```
A ──hello{challenge_A}──────────────────────▶ B
A ◀─auth{challenge_A, sig, accepted}───────── B
A ◀─hello{challenge_B}─────────────────────── B
A ──auth{challenge_B, sig, accepted}────────▶ B
```

The inner signature is over
`canonical_json({challenge, peer_id, purpose: "linkchat/1 handshake"})`,
which proves liveness for this specific challenge rather than mere possession
of a captured frame. On success the connection is bound to the authenticated
peer id, and that binding is what routing uses.

## 8. Transports

A transport moves one signed frame to one peer. It never inspects payloads.
Two properties matter to the router:

| Transport | Delivery | Notes |
| --- | --- | --- |
| `p2p` | immediate | WebSocket, node to node |
| `smtp` | deferred | accepted now, delivered later |
| `local` | immediate | in-process, tests and demos only |

### Selection

```
direct connection open?  ──yes──▶ P2P
        │ no
peer published an address? ──yes──▶ SMTP
        │ no
outbox, retried with backoff; the log heals the rest on next sync
```

The router distinguishes **reachable** (worth dialling) from **connected**
(a socket is open right now). The UI badge reflects the second, because
showing "Direct" for a peer whose machine is off would be a lie.

The outbox is not the durability story. Durability is the log: every record is
on disk before it is sent, and a peer that missed it asks for it on
reconnect. Losing the outbox on restart costs latency, not messages.

### P2P transport

Each node listens on a TCP port and speaks WebSocket. Frames are JSON text
messages, one frame per message, capped at 1 MiB.

**Transport encryption is not provided by default.** A `ws://` connection is
plaintext on the wire; record bodies are already end-to-end ciphertext, so an
observer on the path learns metadata — who talks to whom, when, how much — but
not content. Connections *are* authenticated by the handshake above.
Supplying a `wss://` address puts TLS underneath, at which point the transport
is also confidential; this is not the default because a self-signed
certificate authenticates nobody, and the handshake already does that job.

### NAT, and what is not solved

There is **no NAT traversal**. No STUN, no TURN, no ICE, no hole punching.

A direct connection succeeds when the advertised address is routable from the
dialling machine: same host, same LAN, an overlay network such as Tailscale,
or a forwarded port. Two peers behind ordinary consumer NATs, with no
rendezvous, **will not connect directly** — and the implementation reports
that rather than hiding it: the dial fails, the route drops to `offline` or
`smtp`, and the badge changes.

Solving it honestly means implementing ICE, which means:

- a **signalling/rendezvous service** both peers can reach, to exchange
  candidates. This is why the invite link carries transport hints and why
  signalling is specified as separate from message transport: a rendezvous
  service learns who is trying to talk to whom, and must never be able to read
  content. It cannot: it would carry ciphertext frames at most.
- a **TURN relay** for the pairs — commonly 10–20% — that cannot punch
  through symmetric NAT. A relay is a server, and any claim of "fully
  serverless" that ignores TURN is false.

Neither is implemented. A WebRTC transport implementing both would slot in
behind the existing `Transport` interface without changes above it.

### SMTP transport

A LinkChat message travelling over SMTP is a MIME message with an
`application/linkchat+json` part containing the signed frame. Advisory
headers (`X-LinkChat-Protocol`, `X-LinkChat-Conversation`, `X-LinkChat-Sender`,
`X-LinkChat-Kind`) aid routing and debugging; **no security decision is made
on a header**, only on the signed frame. A human-readable `text/plain` part
explains what the message is; the protocol ignores it.

Sending uses a submission relay configured entirely from the environment
(`LINKCHAT_SMTP_*`). TLS is required unless `LINKCHAT_SMTP_ALLOW_INSECURE` is
explicitly set for local development.

Receiving is where "SMTP as transport" gets awkward, and the protocol does not
paper over it: **SMTP cannot pull.** Something must place the message where
the node can see it. Two adapters are implemented:

- `SmtpListenerSource` — the node runs its own SMTP server and accepts
  deliveries. Suitable for a self-hosted MX or the local dev MTA.
- `MaildirSource` — the node watches a directory of RFC 5322 files, the shape
  produced by `fetchmail`, `getmail`, `procmail` or `mbsync` against an
  ordinary provider mailbox.

An IMAP IDLE adapter is the obvious third and is deliberately absent: it would
be the only component that could not be exercised by the test suite without
live credentials.

**Constraints that are real and are not worked around:**

- Latency is minutes, not milliseconds. Greylisting alone can cost 15.
- Port 25 is blocked outbound on most consumer networks; submission via
  587/465 with credentials is the norm.
- Provider rate limits and spam heuristics apply. A conversation that sends
  thousands of frames over SMTP will get an account suspended. For this reason
  anti-entropy requests to a peer routed over SMTP are throttled
  (`deferredSyncMs`, default 60s) rather than polled at the P2P rate.
- The recipient address is metadata visible to every hop.
- Mail can be silently dropped. The log's sync loop, not SMTP, is what
  guarantees eventual delivery.

## 9. Group messaging and synchronisation

No full mesh is assumed.

**Flood.** After ingesting new records, a node forwards them to every
participant it can reach except the one it received them from. Duplicate
suppression at the log terminates the flood; loops are impossible because a
record is only forwarded the first time it is added.

**Anti-entropy.** Periodically, and on every connection, a node sends its
watermarks — the highest `seq` it holds per author:

```json
{ "kind": "sync_request", "conversation_id": "c_…",
  "watermarks": { "p_ALICE…": 12, "p_BOB…": 4 } }
```

The peer replies with every record whose `seq` exceeds the stated watermark
for its author, batched (200 records by default) with a `complete` flag. An
author absent from the map is treated as watermark 0, so a brand-new
participant asking with `{}` receives the entire history.

This is O(participants) on the wire regardless of conversation length, and it
converges from any starting point: a peer offline for a week, a peer that has
never seen the conversation, and a peer that missed one message all use the
same exchange.

A node serves history to admitted participants. If it does not yet hold the
genesis record it cannot evaluate admission at all, and refusing would
deadlock two peers who both just joined — so it serves. The cost is bounded:
what it serves is ciphertext, useless without the key that only the link
carries.

## 10. Security model

### What is protected

| Property | Mechanism |
| --- | --- |
| Message authenticity | Ed25519 signature over canonical header + body |
| Identity binding | peer id is a hash of the public key |
| Message confidentiality | AES-256-GCM under the conversation key, end to end |
| Header integrity | header is the AEAD associated data |
| Connection liveness | challenge-response handshake |
| Frame replay | signed nonce + 7-day window + replay cache |
| Record replay | message-id deduplication, per-sender sequence |
| Invitation forgery | HMAC-SHA256 under a secret that is not in the link |
| Invitation reuse after revocation | revocation records with explicit grandfathering |
| Private key at rest | mode 0600, optionally scrypt + AES-256-GCM |
| Conversation keys at rest | sealed with a key derived from the device key |
| Local UI access | loopback binding plus a startup token, compared in constant time |

### Transport encryption vs end-to-end encryption

These are separate and are not interchangeable:

- **Transport encryption** protects a hop. Absent on `ws://`; present on
  `wss://` and on any TLS-protected SMTP submission. A transport is trusted to
  carry, never to keep secrets.
- **End-to-end encryption** protects content from everything between authors:
  every record body is encrypted before it reaches any transport, and only
  holders of the conversation key can read it. A relaying participant that
  lacked the key could still carry traffic it could not read.

### What is *not* protected — stated plainly

1. **The link is the capability.** Anyone who obtains it can read the
   conversation. There is no second factor.
2. **No forward secrecy, no post-compromise security.** One long-lived
   symmetric key per conversation. A key that leaks decrypts all history, past
   and future. A ratchet (X3DH + Double Ratchet, or MLS for groups) is the
   correct fix and is not implemented; this is the single largest gap between
   this prototype and a system worth trusting with real secrets.
3. **No member removal.** A `leave` record is a courtesy announcement. There is
   no way to stop a former participant who kept the key from reading later
   messages, because the key never changes. Removal requires re-keying, which
   requires the ratchet above.
4. **Metadata is not protected.** Record headers are plaintext at rest and in
   transit: who spoke, when, in which conversation, how much. Over SMTP the
   participants' addresses are visible to every relay.
5. **Any participant can invite.** By design — the invite secret is shared with
   everyone who joins. There is no admin role.
6. **A participant can equivocate.** Forks are detected and reported, not
   prevented.
7. **The dev MTA is not a mail server.** No DNS, MX, SPF, DKIM, DMARC, auth,
   or TLS. It is bound to localhost and must never face the internet.
8. **No denial-of-service protection.** No rate limiting on inbound frames or
   connections.

## 11. Errors

Rejections carry a stable code. Every one is a security decision, is counted
in diagnostics, and is visible in the developer panel.

| Code | Meaning |
| --- | --- |
| `bad_protocol_version` | unknown `protocol` or link version |
| `bad_signature` | signature did not verify |
| `bad_peer_id` | peer id does not match the public key |
| `bad_encoding` | malformed base64url, JSON, or field type |
| `undecryptable` | body did not authenticate under the conversation key |
| `replayed` | frame nonce seen before |
| `stale` | frame older than the replay window |
| `future_dated` | frame or record dated too far ahead |
| `wrong_conversation` | record belongs to a different conversation |
| `invite_invalid` | invite MAC failed, or the link is malformed |
| `invite_expired` | invite past its expiry |
| `invite_revoked` | invite nonce revoked |
| `not_a_participant` | sender has no admitted join |
| `sequence_conflict` | sender reused a sequence number |

A rejected record is dropped and counted; it is never partially applied.

## 12. Versioning

`protocol` is checked exactly. A future `linkchat/2` peer talking to a
`linkchat/1` peer is rejected cleanly rather than misinterpreted.

Extension rules for a compatible `linkchat/1.x`:

- New record `type` values MAY be added. A receiver that does not recognise a
  type MUST still store and relay the record — it is signed, it counts toward
  sequence numbers, and dropping it would break convergence for peers that do
  understand it — while excluding it from its own views.
- New payload fields MAY be added. Canonical JSON sorts keys, so unknown
  fields do not disturb signature verification of the fields that are present.
- New frame `kind` values MAY be added; unknown kinds are ignored.
- Link parameters MAY be added; unknown parameters are ignored. Removing or
  repurposing one requires a new link version.

---

## 13. Known gaps

Ordered by how much they matter:

1. No forward secrecy or post-compromise security (§10).
2. No NAT traversal (§8), so "direct" in practice means same network, overlay,
   or forwarded port.
3. No member removal or re-keying.
4. Metadata is unprotected at rest and in transit.
5. The outbox is in memory; restart loses queued frames (the log recovers
   them, at the cost of latency).
6. Storage is append-only JSONL read whole at startup. Correct, and fine for a
   prototype; SQLite is the intended replacement, behind the existing storage
   port.
7. No IMAP adapter, so a real provider mailbox needs an external delivery
   agent writing to a maildir.
8. No rate limiting or abuse controls anywhere.
